## 瓶颈与改动

原采样同时运行16个环境，但所有随机策略前向由一个 Python 进程执行；每条轨迹仍单独前向。完整4例 cProfile 对照耗时240.08秒，策略前向累计202.77秒、环境 IPC 累计36.41秒。该对照与原准入共用 GPU，且开启 profiler，不能作为严格加速率分母。

新采样用16个策略进程，每个进程有2个活动环境，总计32。每条访问保留原始种子、单例前向形状、动作采样、环境 reset、authoritative history 和终止规则。只改变访问的调度位置。汇总按原案例顺序；Python、NumPy、Torch CPU 和 CUDA RNG 恢复为原16槽位串行调度结束时的状态。采样副本没有 optimizer 更新，所有访问由同一个当前模型产生，收齐 global32 后才执行主进程 PPO。

更新优化候选采用更大的计算微批、4096 MiB 有界不可变图输入缓存，以及按 TBPTT 窗口汇总 GPU 标量。共享 GNN 每次均重新计算，不缓存可训练特征；损失、每步归约顺序、优化器、裁剪、KL 判定值和更新次数沿用原代码。检测到错误时，在任何相关 optimizer step 之前拒绝更新。

原生 Hungarian/AR 评测仍由原冻结 evaluator 执行，固定12例、保留完成槽位和原 cuDNN 设置。原 r2 manifest、423文件快照、baseline780、zero180和确认集均保留。新 r3 使用独立 manifest；保持展开后的案例、访问ID和种子顺序，按选中批大小重新生成日程哈希。实际微批和采样配置会写入每批更新记录。

## 准入与切换

1. 新 CPU 回归验证 CPU/SMT 分配、逐轨迹终止 RNG、所有标量精确相同、末尾不足 TBPTT 窗口的错误检查、输入缓存释放，以及运行证据绑定。
2. 同一个初始 checkpoint、同32个 canary 案例/种子，与原准入32条完整轨迹逐例比较动作/历史/成本/步数，并核对所有 RNG 状态。
3. 从同一初始状态，在上述完整轨迹上完成两次实际 PPO 更新，与原 `micro8.pt` 比较模型、非空 Adam、ValueNorm 和更新数。micro8 要求精确一致；更大微批沿用原 micro8/4 的容差：模型绝对误差2e-6，Adam 绝对误差2e-6、相对误差2e-5。
4. 用户追加了硬件上限测试要求。旧 r2 的 micro8 参考和新的 micro16 完整对照已完成；原 micro8/micro4 全流程未宣称通过。容量扫描停止尚无正式提交的 r2 服务，保留其全部产物。新 r3 使用独立 manifest，要求选中配置的完整更新对照和新的跨进程非空 Adam 续训验证通过后，再从 B0 开始正式训练。

新扫描及训练采样使用已授权物理核0–31及其 SMT 兄弟核，总范围仍为 `0–31,64–95`。验证进程继续使用原22–29，评估时会与采样竞争这些核心。采样结束关闭策略副本，反向更新前释放这些 CUDA 上下文；下一批采样前释放训练进程的空闲显存缓存。整批计时包含进程启动、采集和关闭。

容量服务约束：MemoryHigh 144 GiB、MemoryMax 160 GiB、禁止 swap；监测服务 cgroup 实际占用达150 GiB或主机可用内存不足32 GiB即停止该探针。实际训练仍保留6 GiB全卡显存余量，训练进程分配器额外为验证器预留2 GiB。正式服务的内存硬上限在部署时取160 GiB与当时可用内存减36 GiB的较小值，随共享主机的实际余量收紧。GPU1 和另外半区 CPU 不在任务范围内。
