# Stage3 checkpoint-boundary update to 192/192

## Material Passport

- Mode: user-authorized checkpoint-boundary configuration update.
- Authorization: use 192/192 after the next checkpoint; continue the same eight-epoch experiment.
- Verification: selected CPU tests, exact serialized checkpoint-state comparison,
  then native CUDA restore and 192-wide capacity admission after the boundary.
- Research status: 192/192 full-trajectory throughput and memory are not yet measured.

## Origin and boundary

Origin: `stage3_h3_r0e8_fresh_20260918_r5_env384_mb128_gpu0`.
Target: `stage3_h3_r0e8_fresh_20260918_r6_env384_mb192_gpu0`.
The origin is currently in local epoch 1. It must finish both PPO passes and final
likelihood replay, save the checkpoint, and publish a complete atomic epoch-1
commit before the watcher may stop its controller. A checkpoint filename alone
does not trigger the update. The in-progress epoch keeps its original 128/128.

The watcher prepares and verifies the migration before sending a signal. Only the
bound controller PID, start time and command line may be stopped. The new controller
then restores the completed epoch-1 state; 192/192 starts at local epoch 2.
This is an automatic checkpoint-boundary process replacement, not an in-place edit
of the running Python process or its immutable source. Original artifacts remain intact.

## Preserved state and configuration

Preserve model tensors, actor and critic Adam moments/step counters, ValueNorm,
Python/NumPy/Torch CPU/CUDA RNG, trajectory schedule, local epoch and update cursor.
Only manifest/recipe hashes and physical microbatch metadata are rebound in copied
checkpoints. Compare all other serialized state exactly before starting CUDA work.

Retain B_SHARED, H3/F4/soft, Train240, 384 visits per epoch, 384 concurrent environments,
64 CPU environment processes and one shared GPU model. Train tau .03, evaluation
tau .3, two PPO passes, LR, clipping, KL thresholds, TBPTT, cache settings and canonical
matching rules stay unchanged. IGA remains frozen with zero solver calls.

GPU0 (`GPU-744c1334-98c8-5318-e799-7ad15eea1fbf`), CPU 0-31,64-95, and their trainer/
validator subdivisions stay unchanged. Preserve the experiment cgroup memory policy
and global oomd settings. The new controller inherits the original 120-hour budget
clock; it does not receive a fresh training budget.

## Exact update accounting

Original R0 epoch 8 contributes 96 inherited PPO updates. Local epoch 1 performs
six updates with 128/128 and commits at 102 cumulative updates. Local epochs 2-8
perform four updates each with 192/192: two minibatches per pass, two passes.
The full continuation therefore has 34 new updates and 130 cumulative updates,
while keeping 3072 training visits and eight local epochs. No LR compensation.
Imported epoch-1 measurements retain their original batch size and measured times.

The stopping policy remains `fixed_eight_epochs_numeric_gates_v1`: no consecutive
validation effect stop and no epoch-4 performance extension gate. Validation120
still runs at epochs 1,2,4,6,8 and controls final checkpoint selection only.

## Admission and monitoring

The new run performs an independent two-case CUDA restore canary and a fresh-process
exact state comparison. It then tests 384 inference slots and 192 backward slots
on three real-graph windows. GPU headroom, allocator ceiling, nonfinite checks,
likelihood/mask consistency, soft/hard KL and complete update accounting remain active.
Failed admission stops the replacement experiment and preserves evidence; no silent
fallback, reduced microbatch, or solver request is allowed. Numerical equivalence
between 128/128 and 192/192 is not claimed.

The short capacity test is not a complete throughput benchmark. Formal epoch 2
records complete sampling/update duration and allocated/reserved memory peaks.
Completed baseline/validation evaluations may be reused only after source, case,
checkpoint and rule hashes match; missing epoch-1 validation is completed before
epoch 2. Tune60 stays out of training and checkpoint selection.

The CPU-only watcher is independent of the interactive session. Before the checkpoint
it consumes no GPU and leaves the current worker running. If the original controller
exits or the wait exceeds twelve hours, it records failure without restarting training.
